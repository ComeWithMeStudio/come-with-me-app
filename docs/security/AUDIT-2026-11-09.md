# Аудит безпеки Come With Me Studio — застосунок

Дата: 09.11.2026. Репозиторій: `ComeWithMeStudio/come-with-me-app`.
Базова `main`: `fbcf455716d14bd12f8d7b6877610f54117541df`.
Робоча гілка: `security/app-scanners-observe`.

## Підсумок і межі

Підготовлено окремий неблокувальний workflow Gitleaks, Semgrep CE, CodeQL та
умовного npm audit. Наявні чотири workflows не дубльовані та не змінені.
Код ігор, застосунку, озвучення, дизайну й медіа не змінювався. Знайдені
недоліки не виправлялися. Злиття, розгортання та запис у хмарні сервіси не
виконувалися.

Критичних підтверджених вразливостей і відкритих секретних ключів не знайдено.
Це результат обмеженого аудиту, а не гарантія їх відсутності. Підтверджено
обхід клієнтського бар’єра платних ігор; приватність дітей і CI-процеси
потребують подальшого опрацювання.

Перевірено весь відстежуваний вихідний код, конфігурації та доступні Git-refs.
Не перевірялися реальні Supabase Auth/RLS/Storage policies, ключі й журнали
акаунтів, Cloudflare/R2 buckets/CORS/IAM, платіжний бекенд, продуктивні HTTP-
заголовки, налаштування GitHub branch protection чи персональні дані реальних
користувачів. Хмарний аудит має бути окремим завданням.

## Пріоритети

### Критичні

Підтверджених немає. Не виявлено привілейованих ключів у фронтенді, виконання
довільного коду з браузерного вводу або прямих клієнтських адміністративних
викликів Supabase/R2. Неперевірені серверні політики не оголошуються безпечними.

### Високі

**H1. Клієнтський preview-стан обходить бар’єр платної колекції.**

- Місця: `game-access.js:4–5,13–16`, `app.js:1`,
  `media/pograymo/figury/istorii/geometry-story.html:18`.
- Код довіряє query-перемикачу та значенню sessionStorage, які контролює
  відвідувач. Зміна стану прибирає UI gate без серверної перевірки оплати.
- Відтворено локально в Chromium: у чистому сеансі захисний екран є; після
  зміни лише browser storage та reload його немає. Жодних ключів або доступу
  до хмарного акаунта для цього не потрібно.
- Наслідок: якщо колекція має бути справді платною, UI не забезпечує
  авторизацію доступу. Це не обхід Supabase-акаунта, не підтвердження витоку
  персональних даних і не отримання адміністративних прав.
- Код прямо зазначає, що перевірка платежів ще майбутня функція. Якщо це
  навмисний публічний demo, потрібно явно відокремити його від тверджень про
  платний захист; інакше пріоритет високий перед запуском продажів.
- Окреме майбутнє виправлення: серверна перевірка entitlement та обмежена
  доставка захищених ресурсів; публічний клієнтський прапорець не повинен
  надавати production-доступ. У цьому завданні це не реалізовано.

### Середні

**M1. Привілейовані завантаження медіа виконуються CI без окремого environment-gate.**

- `.github/workflows/cwm-supabase-media-upload.yml:3–8,21–44` та
  `.github/workflows/cwm-organize-nature-song.yml:2–7,15–40`.
- Workflows отримують `CWM_SUPABASE_STORAGE_KEY` і записують у Storage при
  ручному запуску та push у `main`, що змінює відповідний workflow. У файлах
  не визначений GitHub Environment із додатковим погодженням. Реальні branch
  rules, environment protection і scope ключа через API не перевірені.
- При помилці друкується весь response JSON від сервісу. Витоку не виявлено,
  але довільні error bodies не слід вважати гарантовано очищеними. GitHub
  masking не замінює мінімізацію журналу.
- Рекомендація для окремого етапу: перевірити вузький scope ключа, environment
  approval, доступ до workflow та виводити лише дозволені коди помилок.
  Існуючі workflows і секрети зараз не змінені та не запускалися.

**M2. Межі приватності саме дитячого застосунку не описані повною політикою.**

- У корені застосунку немає окремої privacy-сторінки. `contacts.html:2`
  описує контакти, а політика іншого репозиторію (`privacy.html`) прямо
  обмежує свій scope налаштуванням аналітики головного сайту.
- `app.js:97–109` і `nature-songs.html:4` використовують публічний Supabase
  Storage для аудіо. Такі URL не є секретами; завантаження все одно створює
  мережеву взаємодію з третьою стороною та технічні метадані з’єднання.
- Трекерів GA, запису мікрофона, геолокації, форми дитячого профілю чи
  надсилання імен/відповідей на зовнішній сервер у перевіреному коді не
  виявлено. Є language preference та session preview; самі ці записи не
  доводять збір дитячих персональних даних.
- Потрібні окреме визначення потоків даних/строків зберігання, ролі батьків,
  контактів і договорів із провайдерами. Це ризик незавершеної моделі
  приватності, не висновок про юридичне порушення чи фактичний витік.

**M3. Існуючі Actions закріплені major-тегами, а Playwright установлюється без lockfile.**

- `.github/workflows/game-health.yml:23,38–45`,
  `.github/workflows/audio-storage-audit.yml:13,43`,
  `.github/workflows/cwm-supabase-media-upload.yml:19`.
- Major-теги рухомі. Точна версія Playwright задана, але його транзитивний
  граф не зафіксований відстежуваним npm lockfile. Це supply-chain ризик,
  а не знайдена CVE чи доказ компрометації.
- Новий security workflow вже використовує повні SHA, але старі workflows
  не змінювалися: їх hardening слід погодити окремо. Для інсталяції CI-
  інструментів надалі можна вести окремий відтворюваний граф без додавання
  залежностей до самого дитячого застосунку.

### Низькі

**L1. Політики браузерного захисту потребують перевірки на хостингу.**

У вихідних файлах немає явно заданої CSP/Permissions-Policy/Referrer-Policy
або конфігурації відповідних response headers. Це не доводить відсутність
заголовків у production: хостинг не аудіювався. Багато `innerHTML` формують
статичні/внутрішні дані; сам факт їх використання не є доведеним XSS.
Рекомендовано окремо перевірити заголовки, frame embedding і дозволи камер/
мікрофона; CSP починати з Report-Only, врахувавши inline scripts та медіа.

**L2. Семантичні попередження browser storage потребують підтримки triage.**

Місця `app.js:1,3,14`, `game-access.js:5`,
`media/pograymo/figury/istorii/geometry-story.html:18`,
`media/rozkazhy-meni/piznavaymo-svit/ihry/vid-zerniatka-do-fermy/game.js:182`
не слід автоматично рахувати як витоки: налаштування мови й локальний
прогрес мають інший ризик, ніж персональні дані або auth tokens. Проблему
довіри до preview виділено окремо в H1. Suppression зараз не додано.

## Supabase, R2 і зовнішні ресурси

Публічні аудіо-URL Supabase не містять привілейованого ключа. Браузерних
викликів Auth/admin API у перевіреній версії немає. Привілейований ключ
згадується як GitHub Secret у двох існуючих CI, а не як опубліковане значення.
Налаштування Auth, RLS, bucket policies, CORS, IAM, ротації й журналів не
читалися та не змінювалися.

Використання Cloudflare R2, його SDK, endpoint або ключів у відстежуваному
коді не знайдено. Це не висновок про стан Cloudflare-акаунта чи DNS.
Посилання Google Drive/Docs знайдені в документації, а не як виконувані
дитячі інтеграції. `contacts.html:2` має зовнішнє посилання Google Maps;
для child-facing навігації варто окремо оцінити батьківську межу.

## Доступність, тариф і статус активації

На публічній сторінці репозиторію підтверджено badge Public. За офіційною
документацією GitHub code scanning доступний публічним репозиторіям без
покупки Code Security. Діють загальні Actions quotas/limits. Gitleaks CLI та
Semgrep CE не потребують платних акаунтів; Semgrep Pro/Cloud і ліцензований
Gitleaks Action для організації не використовуються.

GitHub API із поточного середовища повертає proxy Forbidden. Тому наявність
прихованого default CodeQL setup, тариф організації та реальні required checks
не підтверджені. Workflow перевіряє default setup при запуску й пропускає
дубль; невідома доступність позначається unavailable. CodeQL локально не
встановлено й hosted-прогону ще немає. Альтернатива до усунення недоступності —
налаштовані Gitleaks та Semgrep CE, без твердження, що вони заміняють CodeQL.

Перевірки створені для PR до `main`, push у `main` та workflow_dispatch.
Публікаційні jobs не залежать від них; required checks не додані. CodeQL має лише read permissions; ні сирий, ні
очищений SARIF не завантажуються в Code scanning на першому етапі, щоб нові
alerts не вплинули на можливі organization rulesets. Лише очищені місця
виводяться в summary; Security-tab upload потребує окремого погодження. Зміни
підготовлені в окремій робочій гілці, не злиті й не активовані в `main`.
Після погодження потрібно відкрити PR, перевірити перший GitHub Actions run
та Code scanning settings. Конфігурацію, дозволи, redaction і локальний
запуск описано в `.github/security/README.md`.
